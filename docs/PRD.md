# Student Workbench — 第一版 MVP 产品需求文档

- 文档版本：0.3.0
- 日期：2026-11-22
- 状态：可进入实现
- 产品形态：单用户、本地优先的学生开发者工作台
- 相关文档：`APP_FLOW.md`、`TECH_STACK.md`、`BACKEND_STRUCTURE.md`、`IMPLEMENTATION_PLAN.md`

## 1. 背景与问题

软件工程学生同时面对三类工作：

1. 学校教务平台中的课程、课程表等学籍与教学信息；MVP 不把教务平台当作作业来源。
2. 学习通等学习平台中的课程作业、截止时间与提交状态；同一门课可能分布在多个学习平台。
3. 多个软件项目中的里程碑、项目待办、GitHub 活动和本地 Git 风险。

现有工具通常只覆盖其中一类，而且 GitHub 无法看到本地未提交、未推送的工作。第一版 MVP 的目标不是再造一个通用 Todo，而是验证两条核心价值链：

- 能否用统一课程关联教务课程表与一个或多个学习平台的课程待办。
- 本地与远端仓库信息能否转化为可解释的项目健康提示。

## 2. 产品目标

### 2.1 核心目标

- 将学习平台作业、项目待办与手动事项统一为可计划、可完成的 `WorkItem`。
- 只读接入一个教务平台获取课程和课程表，接入一个学习平台获取作业；架构允许连接更多学习平台。
- 用本地统一课程与外部课程身份映射，关联同一门课的课程表和不同来源待办，不靠模糊名称直接合并。
- 将本地 Git 与 GitHub 状态合并为项目健康视图。
- 用“里程碑、下一步行动、阻塞、仓库风险”表达项目进度，而不是用提交数代替进度。
- 外部同步失败时，已有数据仍可查看和编辑。

### 2.2 MVP 成功判据

以下流程全部使用真实数据走通，才认为 MVP 成立：

1. 用户可在工作台内嵌登录向导完成教务/学习平台登录，也可选择保存密码自动填充；复杂流程可回退外部浏览器，验证码由用户完成。
2. 教务平台只读同步课程和课程表，不要求也不虚构作业数据。
3. 学习平台只读同步课程、作业、截止时间和外部完成状态。
4. 同一门课能关联教务课程身份和至少一个学习平台课程身份；架构上可继续加入其他学习平台并聚合到同一课程。
5. 同一平台数据连续同步两次不产生重复课程身份、课程表或事项。
6. 平台登录失效时，界面明确提示重新登录，旧数据不丢失。
7. 至少两个真实项目同时接入本地仓库和 GitHub 仓库。
8. 项目页能展示未提交、未推送、落后远端、CI 失败、开放 PR 和里程碑风险。
9. 用户能维护项目生命周期状态、具体原因、下一步行动和里程碑，并看到确定性的健康原因。
10. 用户能在项目详情直接创建项目待办，并与学习平台作业、手动事项一起进入今日视图；今日课程也能定位相关待办。
11. 断网或外部平台不可用后，本地已有任务和项目数据仍可使用。

## 3. 用户与使用场景

### 3.1 目标用户

- 主要用户：同时推进课程与多个代码项目的软件工程学生。
- 使用设备：个人电脑，第一优先支持 Windows。
- 使用方式：单机、单用户、本地浏览器访问，不开放公网。

### 3.2 核心用户故事

#### 教务与学习平台

- 作为学生，我希望在工作台内嵌登录向导完成平台登录，复杂 SSO 也能回退外部浏览器。
- 作为学生，我希望能选择把平台密码保存到个人电脑的系统凭据库并自动填充，以减少重复输入。
- 作为学生，我希望验证码仍由我完成，并能保留登录会话，以兼顾可用性和平台要求。
- 作为学生，我希望从教务平台获得课程和课程表，而不是被要求同步不存在的作业。
- 作为学生，我希望从学习通等学习平台获得作业、截止时间和原始链接，以便回源核实。
- 作为学生，我希望把同一门课的教务课程表和多个学习平台待办关联起来，而不是每个平台各建一门重复课程。
- 作为学生，我希望自动匹配备选课程可以人工确认，避免同名课或不同学期被错误合并。
- 作为学生，我希望知道最后一次成功同步时间，并希望同步失败不会覆盖或删除旧数据。

#### 项目进度

- 作为项目开发者，我希望把 GitHub 仓库与本地目录关联到同一个项目，以便看到完整状态。
- 作为项目开发者，我希望看到未提交和未推送修改，以便避免工作只留在本机。
- 作为项目开发者，我希望看到 CI、PR 和里程碑风险，以便决定下一步。
- 作为项目开发者，我希望用想法、规划、进行中、受阻、等待、暂停、完结等状态描述项目，并记录具体原因。
- 作为项目开发者，我希望手动维护“下一步行动”和项目待办，以便区分活跃与真正可推进。
- 作为项目开发者，我希望健康状态附带原因和证据，而不是一个无法解释的分数。

#### 统一执行

- 作为学生，我希望在项目详情直接创建项目待办，并和作业、其他手动事项一起进入今日视图。
- 作为学生，我希望分别记录“何时截止”和“何时执行”，以便把计划与截止分开。
- 作为学生，我希望外部状态更新不会覆盖我的本地计划，以便保持对工作流的控制。
- 作为学生，我希望后续看到项目排期和确定性周报，并可选择让 AI 辅助整理复盘内容。

## 4. 功能优先级

优先级定义：

- **P0**：首个可用版本必须完成，并进入验收。
- **P1**：P0 真实使用验证后完成，不阻塞核心闭环。
- **P2**：明确保留的后续方向，当前不设计细节。
- **不做**：与当前定位冲突或风险过高的能力。

| 模块 | 功能 | 优先级 | 验收摘要 |
|---|---|---:|---|
| 本地基础 | 初始化 SQLite、运行迁移、读取已有数据 | P0 | 重启后数据保留 |
| 平台登录 | 内嵌登录向导、外部浏览器回退、可选密码保存 | P0 | 密码入系统凭据库，验证码由用户完成 |
| 教务接入 | 只读同步课程身份和课程表 | P0 | 不同步或虚构作业，课程表来源完整 |
| 学习平台接入 | 只读同步课程、作业、截止时间、外部状态 | P0 | 首个真实适配器为学习通，来源字段完整 |
| 统一课程 | 精确匹配建议、人工确认、多平台课程身份映射 | P0 | 同一课程关联课程表和跨平台待办 |
| 同步与降级 | 同步幂等、失败降级、重新登录 | P0 | 无重复、不覆盖本地计划 |
| 统一任务 | 收件箱、筛选、查看来源 | P0 | 按课程/项目/状态/截止筛选 |
| 统一任务 | 手动新增事项、设置优先级、计划和下一步 | P0 | 本地字段可编辑 |
| 统一任务 | 标记进行中、完成、受阻、忽略 | P0 | 与外部状态分离 |
| 项目管理 | 新建项目、维护生命周期状态与目标日期 | P0 | idea/planning/in_progress/blocked/waiting/on_hold/completed/cancelled/archived |
| 项目管理 | 状态原因、恢复日期和状态历史 | P0 | 特定状态必须说明原因，变更可追溯 |
| 项目管理 | 维护里程碑和下一步行动 | P0 | 项目详情可编辑 |
| 项目待办 | 在项目页直接创建、计划、完成项目 WorkItem | P0 | 自动关联项目并汇总到今日 |
| 仓库管理 | 关联 GitHub `owner/repo` 和本地目录 | P0 | 一个项目可关联多个仓库 |
| 本地扫描 | 当前分支、脏文件、ahead/behind、最后提交 | P0 | 只执行只读 Git 命令 |
| 远端同步 | Issue/PR 数、默认分支检查、里程碑、最后提交 | P0 | 令牌不进入前端和数据库 |
| 项目健康 | 绿/黄/红/未知/无需评估及原因列表 | P0 | 生命周期与健康分离、规则可测试 |
| 今日页 | 今日课程、学习/项目/手动事项及项目风险 | P0 | 课程可定位相关待办，事项可跳转处理 |
| 同步中心 | 手动同步、运行状态、错误、最后成功时间 | P0 | 支持单个连接重试 |
| 使用设置 | 本地时区、临近截止天数、健康阈值 | P0 | 默认值可修改 |
| 数据保障 | 手动 JSON 导出、数据库备份按钮 | P1 | 可恢复核心数据 |
| 自动同步 | 可配置间隔、应用内定时同步 | P1 | 同连接不并发 |
| 提醒 | 截止和风险桌面通知 | P1 | 可关闭 |
| 项目排期 | 里程碑与项目待办时间线、调整计划日期 | P1 | 复用 due_at 和 planned_*，不做完整日历 |
| 学校扩展 | 通知、考试安排、成绩只读同步 | P1 | 仍不自动提交 |
| GitHub 扩展 | 选择性导入 Issue 为 WorkItem | P1 | 不默认导入全部 Issue |
| 复盘周报 | 状态变化、完成事项、里程碑、风险与下周计划 | P1 | 确定性数据生成，无 AI 也可用 |
| AI 辅助复盘 | 用户主动触发、选择数据、生成周报草稿 | P2 | 可接 API 或本地模型，人工确认后保存 |
| 更多适配器 | 第二教务平台或其他学习平台、更多教务内容 | P2 | 复用适配器与统一课程身份契约 |
| 日历与笔记 | 完整日历、课程笔记、知识库 | P2 | 不进入首版 |
| 团队协作 | 多用户、权限、共享项目 | 不做 | MVP 单用户 |
| 学校自动化 | 自动答题、提交作业、刷课、识别或绕过验证码 | 不做 | 明确安全边界 |
| Git 写操作 | 自动 commit、push、pull、清理分支 | 不做 | MVP 只读 |
| 自动 AI 决策 | 自动评价生产力、自动安排全部日程 | 不做 | AI 复盘草稿与自动决策分开 |

## 5. P0 功能需求与规则

### 5.1 教务平台、学习平台与统一课程

#### PLT-001 连接类型与适配器

连接类型明确分为：

- `academic`：学校教务平台，P0 只读取课程身份和课程表。
- `learning`：学习通等学习平台，P0 读取课程身份、作业、截止时间和外部状态。
- `github`：项目仓库连接，不属于课程平台。

MVP 实现两个真实课程平台适配器：

- `academic_portal_v1`：当前学校教务平台，另配 `academic_fake` 测试适配器。
- `chaoxing_v1`：学习通，另配 `learning_fake` 测试适配器。

每个连接独立配置入口 URL、账号标识和允许的平台/SSO 域名。其他学习平台后续实现同一 `LearningAdapter` 契约即可加入，不改变统一课程和 WorkItem。

#### PLT-002 内嵌登录、可选密码保存与外部回退

- 默认在工作台显示内嵌登录向导，账号密码和验证码均可由用户在应用内完成，后端 Playwright 驱动真实平台。
- 内嵌的是工作台向导，不是直接 iframe 嵌入学校网站，避免 `X-Frame-Options`、CSP、第三方 Cookie 和跨域限制。
- 复杂 SSO、特殊二次验证或适配器不支持的页面流程可回退到独立可见 Chromium，由用户在学校页面接管。
- 用户可选择仅本次输入，也可主动开启“保存密码并自动填充”。账号标识保存在 SQLite，密码通过 `keyring` 保存在系统凭据库，键为 `platform:{connection_id}`。
- 密码保存后不回传前端，不写入数据库、浏览器持久化存储或日志；自动填充仅限该连接允许的平台/SSO 域名。
- 验证码、二次验证由用户在内嵌向导或外部页面完成；不保存一次性验证码，不自动识别或绕过验证码。
- 每个连接使用独立持久化浏览器目录保存会话，减少重复登录和验证。
- “清除已保存密码”和“清除浏览器会话”是两个独立操作，均需二次确认。

#### ACA-001 教务课程与课程表

教务平台 P0 只同步：

- 外部课程身份：外部课程 ID、名称、学期、教师（可空）、来源链接。
- 课程表条目：星期、开始/结束时间、起止周、单双周或自定义周次、地点、教师（若平台提供）、来源链接。
- 学期起始日期：第一教学周周一，优先读取教务信息，无法获得时由用户确认，用于把实际日期映射到教学周。

边界与规则：

- 教务平台没有作业时，不显示“同步作业”步骤，不生成空作业或虚假 WorkItem。
- 课程表是独立读模型，不自动变成待办，也不要求用户完成上课这一动作。
- 课程表通过统一课程关联，可在课程详情和今日页显示“今日课程”及相关待办入口；缺少第一教学周周一 `term_start_date` 时提示确认，不猜测教学周。
- 其他教务内容后续按新适配器能力扩展，不混入 P0 作业模型。

#### LRN-001 学习平台课程与作业

学习平台 P0 同步：

- 外部课程身份：外部课程 ID、名称、学期、教师（可空）、课程链接。
- 作业：外部作业 ID、标题、说明摘要（可空）、截止时间、外部状态、原始链接。
- 外部状态：`open/submitted/graded/closed/unknown`。

导入规则：

- 新事项首次导入时，`open` 映射为本地 `inbox`；`submitted/graded` 映射为本地 `done`。
- 后续同步只更新外部字段，不覆盖本地 `workflow_status`、优先级、计划时间、下一步和备注。
- 唯一键为 `(connection_id, external_id)`，重复同步必须幂等。
- 同步未出现的旧事项不自动删除，标记 `needs_review=true` 并提示核实。
- 每项数据保留 `source_url`、`source_updated_at`（若平台提供）和 `last_synced_at`。

#### CRS-001 统一课程与跨平台关联

本地 `courses` 是用户可见的统一课程；每个平台的外部课程由 `course_identities` 表示，多个身份可指向同一课程。

关联规则：

1. 优先使用“学期 + 规范化课程名”精确匹配，教师用于消除同名歧义。
2. 只有一个明确候选时可自动关联；同名、跨学期或信息不足时保持 `unmatched`，必须人工确认。
3. 不使用模糊相似度直接合并课程；用户可手动关联、解除关联或把外部课程单独建成新课程。
4. 修改身份映射后，该来源下的课程表和 WorkItem 统一更新 `course_id`，不需要逐条编辑作业。
5. 同一作业若在两个学习平台重复发布，P0 保留两个来源事项，只归入同一课程，不自动删除或合并来源。

#### PLT-003 同步状态与异常

- 同一连接同时只允许一个同步运行；教务与学习平台可独立同步。
- 同步状态：`queued/running/success/partial/failed/needs_auth/interrupted`。
- 登录失效返回 `needs_auth`，界面引导重新登录。
- 页面结构变化返回 `partial` 或 `failed`，禁止把“解析到空列表”当成“没有课程/作业”。
- 未获得可信数据时，网络失败不修改已有数据；部分数据已可靠解析时可提交，但必须记录部分成功。
- 日志不得包含 Cookie、密码、验证码、令牌或完整个人隐私页面内容。

### 5.2 项目与仓库

#### PRJ-001 项目进度、生命周期与项目待办

项目包含：

- 名称、说明、目标日期。
- 生命周期状态：`idea/planning/in_progress/blocked/waiting/on_hold/completed/cancelled/archived`。
- 当前状态原因 `status_reason`、状态变更时间 `status_changed_at`、可选恢复日期 `resume_at`。
- 自动追加的状态历史，保留前后状态、原因和时间。
- 下一步行动及其更新时间。
- 里程碑：标题、截止时间、状态、完成时间。
- 项目待办：直接关联 `project_id` 的 WorkItem，可在项目页创建、计划和完成。
- 一个或多个仓库关联。

生命周期规则：

- `idea`：想法尚未承诺投入；`planning`：正在规划；`in_progress`：正在推进。
- `blocked`：因具体问题无法推进，必须填写原因。
- `waiting`：等待 review、他人、外部依赖或日期，必须说明等待对象/事件，可设置恢复日期。
- `on_hold`：主动暂停，必须说明原因；`completed`：目标完结；`cancelled`：取消且必须说明原因；`archived`：仅保留历史。
- 只有 `planning/in_progress/blocked/waiting` 参与健康计算，其余状态返回 `inactive（无需评估）`，不继续产生无活动提醒。

项目进度由四个独立部分组成：

1. **交付进展**：里程碑完成数/总数；没有里程碑时显示“未设置”，不显示 100%。
2. **执行状态**：生命周期、具体状态原因、是否存在清晰下一步。
3. **待办推进**：项目 WorkItem 的待处理、进行中、受阻和完成情况；项目待办与学习平台作业一起进入今日页。
4. **仓库风险**：本地与远端快照及健康原因。

`next_action` 只是当前焦点摘要，不自动复制为 WorkItem；用户可以显式将其转为项目待办，避免今日页出现重复事项。

#### PRJ-002 本地 Git 扫描

- 仅扫描用户明确登记的目录。
- 验证目录存在且包含 Git 工作树。
- 使用参数数组调用 Git CLI，不经过 shell 拼接。
- 只执行 `status`、`rev-list`、`log`、`remote` 等只读命令。
- 不自动执行 `fetch/pull/push/commit/clean/reset/checkout`。
- 采集当前分支、脏文件数、未推送提交数、落后远端数、最后本地提交时间。
- ahead/behind 基于本地已有 remote-tracking ref，界面必须注明“可能受上次 fetch 时间影响”。
- 无 upstream、分离 HEAD、目录不可用等情况返回明确状态，不崩溃。

#### PRJ-003 GitHub 同步

- 通过 GitHub REST API 读取公开或已获得授权的信息。
- 采集开放 Issue 数、开放 PR 数、请求当前用户 review 的 PR 数、默认分支检查状态、最近远端提交、GitHub 里程碑。
- MVP 不把全部 Issue 自动转换为任务，避免收件箱噪声。
- GitHub token 仅保存在操作系统凭据库，后端按需读取；前端只能看到“已配置/未配置”。
- API 限流、无权限、仓库不存在和网络错误分别记录，不伪造空数据。

#### PRJ-004 健康规则

健康等级：`green/yellow/red/unknown/inactive`。每次计算返回 `health_reasons`，字段包括规则代码、级别、说明、证据、来源和检测时间。生命周期状态由用户维护，健康等级由规则派生，两者不能互相覆盖。

只有 `planning/in_progress/blocked/waiting` 参与健康评估。`idea/on_hold/completed/cancelled/archived` 返回 `inactive（无需评估）`；这不是数据缺失，也不进入今日项目风险。

默认规则：

| 规则 | 级别 | 说明 |
|---|---|---|
| 项目状态为 `blocked` | red | 展示具体阻塞原因和状态时间 |
| 项目状态为 `waiting` | yellow | 展示等待对象/事件和可选恢复日期 |
| 未完成里程碑已逾期 | red | 以本地时区日期判断 |
| 默认分支存在失败检查 | red | 证据链接到 GitHub 检查 |
| 本地存在未提交修改 | yellow | 展示脏文件数 |
| 本地存在未推送提交 | yellow | 展示 ahead 数 |
| 本地落后已知的远端引用 | yellow | 展示 behind 数和新鲜度说明 |
| `planning/in_progress` 项目没有下一步行动 | yellow | 引导补充下一步 |
| `planning/in_progress` 项目最近 14 天无已知活动 | yellow | 只表示风险，不代表没有工作 |
| 数据超过设定新鲜度阈值 | yellow | 不把旧快照当成实时状态 |
| 参与评估但没有任何成功快照 | unknown | 不强行评估为绿色 |

- 任一红色原因存在即为 `red`；否则任一黄色原因为 `yellow`；数据完整且无风险为 `green`；非评估生命周期直接为 `inactive`。
- 阈值写入本地设置，健康计算使用纯函数，不直接访问数据库或网络。
- 不计算“生产力分数”，不按提交数排名。

### 5.3 统一 WorkItem 与今日页

#### WRK-001 统一事项与项目待办

- 来源：`manual/learning/academic/github`；P0 外部 WorkItem 来自学习平台，教务课程表不生成 WorkItem，GitHub 来源仅供后续兼容。
- 类型：`assignment/exam/task/milestone`。
- 本地执行状态：`inbox/planned/in_progress/blocked/done/dismissed`。
- 本地字段：优先级、截止时间、计划开始/结束、预计分钟数、下一步、备注。
- 学习平台同步字段与用户字段分离，同步不得覆盖用户编辑。
- 学习平台事项通过 `course_identities` 归入统一课程；修改映射时整批更新，手动事项仍可直接选择课程。
- 项目详情提供“新增项目待办”，自动写入 `project_id`、`source_type=manual` 和 `item_type=task`，并复用同一 WorkItem API，不另建项目 Todo 模型。
- 项目待办同时出现在项目详情和统一收件箱；项目下一步摘要只有用户显式转换时才成为待办。

#### WRK-002 今日页

今日页统一汇总学习平台作业、项目待办和其他手动事项，按以下顺序展示：

1. 已逾期且未完成。
2. 今日计划执行。
3. 即将截止但尚未计划。
4. 受阻事项。
5. 红色项目健康原因。

每个事项显示课程或项目归属，项目待办还显示项目生命周期状态。即使项目暂停或完结，已明确计划到今天的事项仍保留并标记项目状态，避免静默遗漏。

默认“即将截止”为未来 3 天，可在设置中修改。用户可在今日页直接调整计划、标记完成或跳转原平台/项目详情。

## 6. 功能边界

### 6.1 数据边界

- 本地 SQLite 是用户编辑数据的唯一事实来源。
- 教务平台是其外部课程身份与课程表的事实来源；学习平台是其外部课程身份、作业与提交状态的事实来源。
- 本地 `courses` 是统一课程事实来源，`course_identities` 保存用户确认或精确匹配产生的跨平台关联；外部课程名变化不会自动拆散已确认关联。
- Git 与 GitHub 是仓库快照的事实来源。
- 项目健康是派生读模型，不手工编辑，也不作为独立事实来源。
- MVP 不做教务/学习平台双向同步，不做 GitHub Issue 双向同步。

### 6.2 自动化边界

- 只读取完成个人工作台所需的信息。
- 不自动点击提交、答题、播放、签到或评教。
- 不绕过验证码、访问控制或平台频率限制。
- 不抓取与任务管理无关的同学、教师或成绩隐私数据。
- 真实教务/学习平台接入需遵守对应平台条款和访问频率要求。

### 6.3 运行边界

- 服务只绑定 `127.0.0.1`，不提供公网部署和多人访问。
- MVP 无账号系统；本地 Origin/Host 校验不能被视为公网认证方案。
- 离线时支持读取和编辑本地数据；外部同步明确标记不可用。
- PWA 安装和 Service Worker 离线缓存不属于 P0，避免缓存陈旧 API 或敏感响应。

## 7. 非功能需求

### 7.1 可靠性

- 教务课程身份、课程表、学习平台课程身份和作业同步均具备幂等测试。
- 统一课程精确匹配、歧义待确认、手动改绑和跨平台聚合具备领域测试。
- 所有健康规则具备表驱动单元测试。
- 本地 Git 测试使用临时仓库，不依赖开发者真实项目。
- 应用在启动时将异常中断的 `running` 同步标记为 `interrupted`。
- 数据库启用外键和 WAL，写入使用事务。

### 7.2 安全与隐私

- GitHub token 和用户主动选择保存的平台密码均使用 OS 凭据库；每个平台连接使用独立浏览器目录。
- 平台密码只可由后端在允许域名上自动填充，保存后不回传前端；同一 OS 用户账户下的凭据访问风险需在设置中说明。
- 密码、验证码、令牌、Cookie、数据库、浏览器目录和日志均不进入 Git。
- 日志默认脱敏，不记录完整响应体、作业正文、密码或验证码。
- 后端拒绝非允许 Host/Origin 的写请求。
- 外部平台链接仅由用户主动打开；内嵌登录只展示本地向导和适配器明确返回的挑战内容，不任意嵌入第三方页面。

### 7.3 可用性

- 所有列表具备加载、空、错误和过期状态。
- 健康状态必须同时显示文字与图标，不能只靠颜色。
- 时间存储为 UTC ISO 8601，界面按用户本地时区显示。
- 同步运行不阻塞查看和编辑本地数据。

### 7.4 可维护性

- 教务/学习平台适配器只返回标准 DTO，不直接写数据库。
- 健康规则不依赖 ORM、FastAPI 或前端。
- API 使用 `/api/v1`，Pydantic 响应模型生成 OpenAPI，前端类型由 OpenAPI 生成。
- 数据库变更只能通过 Alembic 迁移。

## 9. 后续决策点

P0 完成后根据真实使用回答：

1. 教务/学习平台适配器失败主要来自登录、页面结构还是访问频率？
2. 项目健康提示是否有助于行动，还是产生过多黄色噪声？
3. 用户更需要自动同步与提醒，还是更需要周报和日历？
4. 是否需要选择性导入 GitHub Issue，而不是继续扩展手工事项？

只有这些结论明确后，才进入 P1/P2，避免提前建设完整日历、AI 或多平台框架。
